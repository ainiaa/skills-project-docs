# 产品工作流与共享结论

资料条件与推荐方案判断见[资料条件与产品质量](input-and-quality.md)；正文、图和交付格式见[阅读与变更](reading-and-change.md)。资料充分直接整理，不重新访谈；是否充分按下述澄清判断，不以输入篇幅或草稿状态判断。

## 按需选择阶段

先按用户要做的事选择加载路径，资料出现缺口时再切换所需阶段：

| 当前任务 | 加载与边界 |
|---|---|
| 评审现稿 | 读取原稿、质量约定及工作流的评审/走读部分；不为评审加载生成模板或原型交付要求。 |
| 整理或局部修订已有需求 | 使用对应模板及写作/修订约定；已有资料足够时直接整理，不诊断未调用的探索能力。 |
| 探索目标或澄清关键业务选择 | 按工作流选择当前主导能力，调用前按[依赖与适配](dependencies.md)检查该能力是否真实可用；缺失只说明受影响部分，不伪称已运行。 |

| 缺口 | 主导能力 | 下一步 |
|---|---|---|
| 目标或方向不清楚 | Superpowers brainstorming | 明确用户、问题、目标和候选方向 |
| 方向明确，业务决策未闭合 | Matt Pocock grilling | 按前置条件分轮问关键问题，或按用户要求保留草稿 |
| 术语混用 | domain-modeling | 将概念定义和近义词约定写入已有术语表 |
| 资料足够 | 本Skill组织PRD | 直接写作，仅处理冲突或影响结果的缺口 |
| 页面或状态难理解 | PRD内嵌示意 | 原型仅按明确授权，覆盖要求见prototype.md |

这是产品接入层适配，不声称完整照搬上游。一次只有一个访谈主持者，切换传递已知结论；只有核心目标无法满足才重新探索。复用domain-modeling的GLOSSARY-FORMAT.md与ADR-FORMAT.md；没有真实不可逆取舍不另造ADR。既有系统先读[brownfield约定](brownfield-delivery.md)。

按任务核对目标用户与场景、问题与价值、范围与优先级、功能规则、页面流程、数据状态、非功能与依赖、验收与落地八个维度；不要求凑满章节，不适用需有理由。正式PRD是单一规则真源。

## 写作与修订基线

生成完整稿或大改前，先在已有追踪/评审记录中简记本期独立诉求、已定规则、明确不做项及候选事项，并关联来源；已有记录直接复用，后续只更新变化。它用于检查保留，不复制一份业务规则，也不增加文件、状态机或用户签字步骤。简单改动可用一行前后变化和保持项表达。

复杂业务先确定背景、问题、范围、场景处理的主干，再由场景结果推导流程和产研变更。每个场景交代前提、触发操作、各对象及字段变化、金额/状态结果、异常后的下一步及验收；同类场景使用一致粒度，不能只给部分场景写结果表，其他只列名称。共用规则集中定义，但每种场景的具体预期必须能直接找到。候选账务及其依赖结果始终标候选，不替财务批准。

修订默认定点修改，先列影响的正文、图、页面、数据、接口及验收；只有核心规则或整体结构确需变化才重写。合并范围清单不能删背景，简化文案不能删场景、字段预期或上游约束；新增技术发现先核是否属于已授权范围，候选存储/架构不自动变成需求。按下述保留走读复核整稿有效诉求，再检查本轮影响链，不只看新改段落。

默认以Markdown作为主交付；输入为Word/PDF不构成同格式输出要求。主文内容检查结束后再集中生成用户要求的Word/PDF，规则、图及表格使用同一业务主文；内部修订不必每轮另出完整排版版。延期排版不等于延期已能完成的场景、页面图或影响核实。最终格式同时核对图表及必要引用可达：保留真实链接和随包目标，或内置相应内容，不能把仅有标签文字当成附件可用。局部排版问题只重验受影响页。这个顺序不增加一轮“可以开始生成吗”的确认，也不跳过明确授权的最终文件交付。

## 生成前澄清与未决分类

生成、修订或评审PRD前，先从已有资料和有效决定中消除可查证的缺口；明确事项不重复问。只澄清会改变本次业务结果、权限、范围、状态、历史适用或验收预期的关键问题，不为模板空栏补访谈。明确沿用且足以确定结果的既有约定也算已决；本期未改变的处理不因未展开实现细节就重新设计。只有能指出本期不同答案导致的具体结果差异时才升级业务问题，不因存在理论上的其他方案追问。写作或走读中才发现这类歧义，也要转回澄清，不能直到交付才列一串业务“待确认”。

核实现有规则要同时查相关业务文档、配置样例和源码，不能只查代码后把仓库已有约定重新问用户。缺现网配置或运行值不自动构成业务未决：先按可用约定写目标行为并计算条件结果，说明尚缺哪些实现证据；只有规则本身存在会改变结果的选择才提业务决定。用户已要求生成或修订时，未获答复只阻塞受影响的规则和验收，仍须将已明确的独立部分落实为可阅读的PRD正文，并明确整稿尚未闭合的范围；不能仅交“修订准备”，也不能将取得所有生产配置作为交付独立正文的前置条件。这不允许把未决分支写成已定规则或宣称整稿可实施。

| 类型 | 判断与处理 |
|---|---|
| 业务未决 | 不同答案会改变规则或可观察结果。说明已知结论，提出当前最关键问题及必要的推荐、替代与取舍，等待回答后再确定受影响规则和验收；相关前置决定未定时不连问后续细节。 |
| 技术待核实 | 业务行为已明确，尚缺现有字段、接口、存储或实现兼容证据。列核实内容及阻塞部分，可继续明确的业务规格；核查若暴露会改变业务结果的选择，转为业务未决，不能笼统交给研发决定。 |
| 待批准 | 内容已明确，仅缺正式签核或授权。保留规则和真实确认记录，说明批准范围，不为签核重复询问业务，也不自动授予实施权。机器元数据仍沿用草稿／待确认／已确认等既有合法值；“待确认”须在上下文说明是业务未决还是待批准，不新增状态枚举。 |

例如，“最多200字”若尚无可用计数约定，字符、码元等口径会改变边界验收，须先澄清；用户已明确UTF-16码元口径时，不再追问同一决定。存储字段是否支持该规则属于技术核实，文档尚未签核属于待批准，二者都不能把已明确规则变成业务未决。

仅在用户明确要求暂缓决定、当前无法回答或要求先出带未决事项的讨论草稿时，可保留业务未决并继续独立部分；已明确暂缓的问题不再催问。普通“草稿”称呼或模板默认草稿状态不构成暂缓授权。提问尚无回复时可以整理不受影响的部分，但受影响部分保持未完成，不以超时默认同意。用户已要求先出未完成草稿时，新发现的关键问题仍要提出并标明阻塞，同时交付已明确的独立部分，不能只提新问题就停止全部草稿。标明具体问题、影响的规则与验收、可推进和阻塞部分；不替用户选择参数，也不把依赖未决答案的场景写成确定可执行的验收。

交付前重新检查正文、表格、图、验收及补充材料里的未知项：业务未决是否已询问或获明确暂缓，技术核实是否夹带业务选择，待批准是否被误写成规则不清。发现未提出的关键业务缺口，先问再交付受影响部分；没有关键歧义就直接整理或给评审结论，不追加一轮复述签字才算完成。

## PRD评审

先核对来源完整性，再按上述澄清规则和需求保留走读检查实际正文、图及验收。默认交付具体问题、依据、影响及下一步；仅评审不自动修改或重写原稿，不要求原稿先转换模板、补FR/AC或生成新PRD才能给出内容结论。结构检查仅在输入适用时执行，格式缺失与业务缺陷分别报告。

用户觉得问题多或过于严谨时，先合并相关发现、区分可查事实与真正决策，压缩解释；不能仅凭“评审稿”或这类反馈降低已要求的审查标准，把会改变业务结果的异常、恢复或历史规则推给研发。反例采用假设时先说明条件并核查可用资料，不能据假设就要求业务二选一；查不到实际规则才说明具体缺口及其影响。

文档错误有明确已决依据时，指出应如何纠正；只有用户已授权修订才直接改。正文与验收等业务口径互相冲突、来源又无法判定时，先提业务选择，不按内容位置自行选边，也不把推荐当决定。关键问题未答只阻塞相关规则和验收的结论，不阻止同次交付已查明的独立评审意见；技术证据待核实与待批准分别报告。评审建议、模型检查及结构通过都不替代业务决定或真人批准。

## 来源与决定

先核对正文、嵌入表格/图、相关评论/标注和全部回复的读取完整性；飞书正文用lark-doc，评论/回复用lark-drive，检查分页和锚点。冻结快照注明版本、时点和缺口，不声称读过线上最新版。把来源事实、明确决定、建议/假设和未决分别记录在已有证据或追踪文件，不建立新数据库。

按明确修订关系合并口径；未解决评论不等于没有结论，局部认可不能扩展全文确认，未回复不是同意。冲突按时间、适用范围及修订关系判断，不能按资料类型暗自选边；身份或指代不明则保留受影响分支。暂停记录阶段、已知结论与下一个缺口；恢复只核实变化。

## 需求保留与恢复走读

修订前与交付前各核对一次，复用需求追踪或现有评审记录，不强制新增文件。范围限本次输入及直接相关的有效约定，不遍历整个系统补需求。

1. **查覆盖。** 从原始输入、业务后续确认和仍有效的关联约定提取独立诉求；逐项定位当前主文规则、适用图及验收。标明保留、修改、明确撤出或资料缺失。不能只对照上一版；只有编号、附件中的提及或源码实现，不代表主文已承接。没有用户撤回依据的遗漏须恢复，不能借“精简”或“外围不改造”移除既有交接约束。旧FR/AC原编号保留，撤出可留空号。
2. **核确认。** 新确认只覆盖明确内容；被否定的假设及其推演同步退出。用推荐、替代、取舍及阻塞部分表达真正未决，不把“风险不大”变成全部方案获批，也不重复询问已决定事项。
3. **走结果。** 用带具体标识和数值的一组对象走正常路径，再按本期风险选择混合状态或异常。逐步写出采用依据、只读/写入对象、用户看到的结果、不变值，以及谁在何处做什么才能继续。业务余额、记录金额和受影响的账务/派生余额分别复算，不能只算业务表；新方案未决不免除按已知规则算出现状差额。凡本次写入可能无返回结果，区分成功、确定失败、结果待核实；未收到响应不能推定原值未变。重试须有核实入口、判定依据、所查结果的对象标识及允许条件；图与正文必须指向同一对象，不能用含糊的“原记录”混淆业务来源和本次结果。缺失就明确为设计缺口，不能以“说明原因”“核实后重试”视为闭环。
4. **核图与下一步。** 从实际页面反馈沿图的每个相关出口继续，比较顺序、影响范围、取消/重试和结束结果。局部冲突、公共故障及数据子任务失败不能无依据扩大为整批/原业务失败。出口确实转人工或本期不处理时，交代接手角色、现有渠道或待核实入口；不为补闭环新增审批、任务平台或外围补偿。

发现项分清：文档矛盾/遗漏须修；业务待决给候选与决定角色；实现能力未核实说明阻塞部分；范围外仅说明影响。结果记录具体对象和推导，不用标题齐全、图片数量或“已检查”替代。无源码时照样完成业务走读，实际后台兼容及入口承载另标待核实。

## 确认与修订

文档可为草稿，同时保留已明确规则。确认绑定真实记录、当时版本及对应需求/AC/所引规则；模型不能授予批准。规则有语义变化则重新确认受影响部分，共享规则影响不明则人工复核；保留未变记录原文，不批量替换版本制造签字。

机器检查旧单文件仍用 `--baseline old-prd.md`；拆分文件显式成组：

```bash
python3 <集合>/scripts/validate_product_doc.py --file prd.md --tracking prd-traceability.md \
  --baseline old/prd.md old/prd-traceability.md \
  --baseline next/prd.md next/prd-traceability.md
```

每组1或2个文件，按从旧到新重复；不猜追踪文件名。旧拆分主文独自不能构成有效基线。两文件须同目录、同版且主文链接追踪；仅版本/状态元数据变化、FR及AC/来源/共享业务内容未变时可证明旧记录一致。主文与追踪相互链接在显式文件对内比较；当前FR自身、其绑定来源或共享内容引用的其他文件、图片和外部链接仍未冻结，旧确认须人工复核。明确属于其他FR或其绑定来源的直接链接不扩大本FR的确认范围；未绑定来源、归属不明的引用及reference-style链接定义仍按全文保守处理。单文件与拆分格式转换也不自动授予继承；外部资料内容与真实确认人身份不由校验器证明。

结构失败修实际文件或声明，不删来源、改业务口径凑通过。正文格式约束和分角色结论见reading-and-change.md；`--review`只观察标题并给问题提示，handoffReview.status=not_run不会自动变为通过。

## 验证与交付

先完成上述内容走读，再运行适用结构、资源与浏览器检查；需要时独立Builder Check实际读成品。内容复核按读者任务检查：业务能否找到场景的操作和最终结果，研发能否找到页面/记录字段/接口变化及阻塞，测试能否据输入准备确定预期。复用review.md或回复，为每类实际相关读者给具体问题、可从成品得到的答案、章节/表格位置及缺口；不适用的角色说明原因，不为凑表新增流程。同时指出重复说明、偏离主线的实现细节及埋得过深的结论，按保留基线核实后删减或重组，避免每轮评审只补内容。复杂业务另选会改变结果的操作顺序或混合状态作反例；复核范围须包含保留基线，不能只审本轮新增段落。没有具体走读依据，不能用“未发现问题”概括整稿通过。

复杂业务在已有评审/追踪记录里保留以下少量实际证据，不再另造检查文件；简单变更不套用：

| 证据 | 能从实际材料复核什么 |
|---|---|
| 判别性反例 | 一组明确对象及操作顺序，逐步数值和结束关系；按来源规则推导，假设及未决分开，不能只写“待财务确认”而省去已知结果。 |
| 真实入口及使用链 | 来源定位→实际打开动作/可见条件→目标对象操作前后仍能查看→返回/规则/既有导出等适用落点。分别核独立组装链，未核实不能写成现有；有源码且已授权核实的部分不能仅留“研发再查”。所需页面图实际存在并与该入口一致。 |
| 保留对照 | 原始独立诉求（含配套提示与候选）→当前正文/图/验收位置，或明确撤回/排除依据；不能把建议升为硬需求，也不能因简化或“外围不改”悄悄丢弃。修订后读回当前成品，不用旧章节名或未落盘的修改声称完成。 |

分别报告当前版本的文档缺口、业务待决、技术待核实、模型复核、真人确认及可推进部分，不能互相推导。元数据通过不等于设计无阻塞；没有真实试读就写未验证。有限行为评测见[evaluation.md](evaluation.md)。

仅写PRD的任务到文档交付结束。技术设计、业务代码、PDLC、提交和外发分别按明确授权处理；完整原型已授权时保留完整范围，不因先写PRD或局部修订缩减，也不因未来可能需要而追加原型。用户后续授权实施，才交接必要设计与计划。
