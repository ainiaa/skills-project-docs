# 活动报名有效人数与待核实明细

> 产品版本：draft-1
> 状态：草稿

作者：Jeff.Liu

## 业务背景与这次变化

运营每周合并两渠道的多个场次报名，现有命令按行计数。组织者需要按本场已确认有效报名准备座位，同时看见需核实的原记录。建议沿用运营现有命令链，调整快照统计并增加待核实明细；组织者仍确认最终座位数。有异常时结果只是已确认基数，不承诺最终完整人数。规则来源为[模拟业务澄清](clarifications-simulated.md)，不代表真实人员批准。

| 对象 | 本期变化 | 边界 |
|---|---|---|
| 场次人数 | 行数改为本场已确认有效员工人数 | 员工号可信，跨场次分别算 |
| 核实结果 | 返回原记录字段及待核实原因 | 运营回原渠道处理；组织者作最终确认 |
| 合并 CSV | 仅作为当前输入快照读取 | 不删行、不覆盖、不自动纠正，不回填历史结果 |

## 计数与异常处理

先限定所选场次，再按非空员工号分组。同员工同场次所有记录共同判断：若同时存在 confirmed 和 cancelled，本员工整组是状态冲突，暂不计入，保留该组所有原行待核实；不能先过滤 cancelled 后掩盖冲突。只有 confirmed 而无冲突的组计一席；只有 cancelled 的组不计。跨场次各自有效，不把 S1 的状态/重复影响到 S2。

缺 employee_id 的行单列待核实，不猜身份、不将多个空员工号合并成同一人、不计入确认人数。异常明细包含 record_id、employee_id、session_id、status、source 和原因；状态冲突保留组内全部原行，缺员工号保留该原行。相同员工同场次的多个 confirmed 本身可按规则确定一席，不列为必须人工核实；原 CSV 和记录来源仍保留。

只读当前导出快照。已确认人数与待核实原记录数是不同指标，不能将异常行数当潜在人数或把二者相加称最终人数。有异常须显式说明本结果未含全部待核实情况；组织者在运营反馈后确认最终座位数。

| 样本场次 | 采用的原记录 | 目标结果（规格演算，执行证据另采） |
|---|---|---|
| S1 | R1/R2 合一席，R3 一席，R6 一席；R5 取消；R7 缺员工号 | 已确认基数 3，待核实 R7；不称最终完整人数 |
| S2 | R4 E01 confirmed | 已确认基数 1，待核实为空；不被 S1 重复影响 |

## 操作与恢复

运营沿用 input/session 的命令入口，选择已取得的合并表快照与场次。读取后得到已确认基数和异常原记录，回到各记录 source 对应原渠道核实员工号/状态；取得修订快照后重新运行，原快照及既有结果保留用于回溯。组织者接收结果并确认最终座位数；实际人员未指定，本期不建设新回写或消息通道。

选中场次没有记录，显示确认数 0、异常为空，并说明“本快照无该场次记录”；不能据此证明活动存在或取消。缺失列、无法读取/解析文件、非约定状态或关键定位字段缺失时，提示具体原因，不能把失败显示为正常 0 或给出可用人数；运营修复输入取得新快照后重跑。非约定状态不是合法 cancelled。业务数据异常（员工号缺失、已知状态冲突）按上节单列，不使其他有效员工失去计数。

本期无新增页面、账户或权限。操作者继续使用已有读取文件权限；无数据库、外部写入或自动修改原渠道。异常名单仅随既有获授权业务交接流转，不增加公开链接。历史文件仍可作为快照输入；不改变其内容，不静默替换此前已交付结果。

## 关键验收场景

| ID | 输入与操作 | 可观察预期 |
|---|---|---|
| AC-001 | 原样样本运行 S1、S2 | S1=3 且 R7 待核实；S2=1；原 CSV 字节不变；S1 提示有待核实 |
| AC-002 | 仅 E01/S1 confirmed 两渠道 R1/R2，以及 E01/S2 confirmed R4 | S1=1、S2=1；调换行/渠道顺序结果不变 |
| AC-003 | 同员工同场次同时 confirmed/cancelled；另有 E02 confirmed；另场次同员工 confirmed | 冲突组不计且其全部原行标状态冲突；E02 计一席；另场次员工计一席；取消独组不计 |
| AC-004 | 同场次两个不同 record_id 的缺员工号 confirmed 行 | 已确认基数 0；两条原行分别保留为缺员工号异常，不合成一人；每条含五个原字段和原因 |
| AC-005 | 空数据或样本无所选场次；文件不可读/缺必要列/非约定状态/关键定位字段缺失 | 前者 0+无记录提示；后者明确失败原因，无有效人数结果；不改原表；修复快照后可重跑 |
| AC-006 | 运营按 R7/source 核实员工号，取得新快照，将 R7 补为不与其他员工冲突的 E05，再运行 S1 | 新快照确认基数 4、R7 不再因缺号待核实；旧快照及旧结果仍可追溯，组织者作最终确认；本功能不自动回写 |

## 交付与待核实

本稿规则已由本次模拟角色答复支持，无需要重问的核心计数口径。未指定的正式负责人和实际截止时点属于落地待落实；不影响本次快照规格，但阻止声称实际报数流程已接收。本稿不代表真实审批或生产落地；当前本地模拟实现按当前设计和新采执行回执核验。

本次模拟消费者为运营，模拟输出契约与输入防护已由范围澄清明确，按当前设计实施；真实消费者兼容、实际Owner和渠道仍待核实，不据模拟决定扩大生产适用范围。详见[需求追踪与来源](prd-traceability.md)、[当前设计](design-current.md)、[方案决定](decision.md)。无页面和新系统，不交付原型；纯 CLI 规则增量用场景表表达，没有新增跨系统交接或页面图。
