# 合成案例：订单异常进度查询

作者：Jeff.Liu。所有业务资料、角色、确认、审批及效果数据均为虚构的测试输入，不代表真实组织决定。本例不是生产业务服务；身份与数据为固定测试值，不具备真实认证。

## 原始问题与决策（L0–L2）

虚构业务原话：“订单异常后不知道处理进度”。场景目标：有权用户可查看异常状态及下一步提示。协调者在业务无 AI 时将此稿带回业务确认；业务有 AI 时接收其草稿并核对同一来源。两种方式均不由 AI 签署确认。本例用测试输入模拟选定研发方案，非研发分流另按生命周期规则处理。

## 正式需求 FR-EX-1 v1（L3）

本文件是案例唯一需求主文；只为单条合成订单 EX-1 演练完整追踪。

| AC | 输入 | 预期 | 测试 |
|---|---|---|---|
| AC-1 正常 | owner，EX-1 | investigating 和 Wait for support | test_authorized_user_sees_next_action |
| AC-2 越权 | visitor，EX-1 | PermissionError | test_other_role_is_denied |
| AC-3 无数据 | owner，unknown | not_found 与 Check order ID | test_missing_order |
| AC-4 非法输入 | owner，空白 ID | ValueError | test_empty_order_is_invalid |
| AC-5 源失败 | available=False | ConnectionError，不假报成功 | test_source_failure_is_visible |

业务 UAT 与发布批准仅模拟，不以这些输入证明实际业务批准。效果口径：真实试点应先收集询问进度次数基线，再确定观察期和 Owner；本例没有收益数据。

## 设计与实现（L4–L5）

标准库 Python CLI，lookup 接收固定测试角色和订单，先校验角色/参数，再查固定合成数据。没有数据库、网络或外部写入。真实服务必须使用可信认证主体和受控数据源，本例不提供这些适配。测试先失败，再实现 status.py；构建身份为该文件 SHA-256。

## 验证与隔离发布（L6–L9）

主仓测试 scripts/test_lifecycle_delivery.py 在临时目录运行上述五项断言，保留测试输出，复制同一构建字节到独立 release 目录，再由新进程运行 CLI 并校验输出。被测构建与部署字节必须一致。将部署副本替换为会抛异常的损坏制品，实际运行冒烟确认失败、记录阻断与恢复条件，再从已测源码构建复制原字节到恢复目录，核对摘要并重跑冒烟。该操作验证本地制品执行及恢复，未部署真实订单系统，也未验证数据库/外部动作补偿。

## 交接（L10）

操作者运行 python3 status.py owner EX-1。真实接手时应核查身份来源、权限、配置、监控、支持人和变更历史；这些不在本例中。模拟观察记录不代表效果达成。需求变为 v2 时保留 FR-EX-1、正式主文路径和已有产物 ID，沿版本依赖使受影响证据待复核，不创建第二条需求。

## 分支结构演示

`branched-record.json` 是额外的**纯结构模拟**，不由上面的 CLI 案例执行，也不证明通知功能已经实现。一个合成痛点关联查询与通知两条需求，两个工作项共同进入一个构建；试点与全量发布引用同一个构建，各自有环境和用户范围。模拟的试点已完成，全量授权待确认、部署阻塞，效果仍在观察中。因此只记录试点分支完成，不能声称整个交付或业务效果完成。

变更共享构建版本时，两个发布分支和效果交接均须复核，最初问题及两条需求不应因此被改写。此文件与正式单功能演练主文保持同一目录，用不同 subject_ref 明确区分交付范围。
