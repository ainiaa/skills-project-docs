# 阶段、分流与交接

作者：Jeff.Liu

L0–L10 是规范阶段标识，非强制全局串行状态机。真实项目可按风险合并活动，但每个对象、版本、环境和发布批次分别保留结果，不通过编号迁移旧审批。

| 阶段 | 工作与主要产物 | 推进依据 |
|---|---|---|
| L0 受理 | 原话、来源、场景、影响、问题身份和负责人 | 问题可定位；未知与敏感边界明确 |
| L1 调查 | 现状证据、复现、规则与知识缺口 | 区分事实/反馈/假设/技术未知，不要求业务先懂技术 |
| L2 价值与分流 | 目标、替代/不做选项、研发或非研发决定 | 决策责任人、理由、范围与来源可追溯 |
| L3 需求与验收 | 唯一正式 PRD、规则、FR/AC、范围与例外 | 关键规则及验收由对应负责人确认，绑定具体版本 |
| L4 产品及技术设计 | 流程、交互、接口、数据、权限、依赖、测试与恢复设计 | 项目要求的评审覆盖需求及异常，风险有负责人 |
| L5 开发与评审 | 工作项、测试先行证据、变更/提交、构建、评审 | 关联需求及验收；正常、边界、异常测试和项目检查通过 |
| L6 测试 | AC→测试场景、执行记录、缺陷与复测 | 每项必需 AC 至少有适用测试或人工场景，绑定场景版本、构建、环境和范围 |
| L7 业务验收 | UAT 场景、结果、责任人和来源 | 对相同需求与适用构建完成业务确认，不用技术单测替代 |
| L8 发布准备与授权 | 发布包、窗口、目标环境/批次、依赖、迁移/兼容、备份、回退/补偿、监控、支持和通知 | 必要批准绑定构建、范围、环境及有效期；被测包与待发布包一致或重新验证 |
| L9 部署与核验 | 实际部署回执、健康检查和业务冒烟 | 版本、环境、范围一致且核验通过；各批次分别记，局部成功不代表全量成功 |
| L10 效果与交接 | 指标口径/基线/观察期、业务效果、操作和配置知识、支持/维护交接 | 接收人可据资料处理；效果有数据与确认，未到期为待观察 |

测试未执行、失败、跳过、阻塞分别记录，均不能算通过。例外遵循组织规则，保留影响、风险、批准人及期限，不以例外字段绕过不可接受的阻断。业务验收与上线授权分开。

需求/规则/AC 变化先沿真实依赖定位受影响设计、代码、测试及审批；构建、环境、配置、迁移或发布范围变化则重新检查相关测试/UAT/授权。标“待复核”，保留旧确认及适用版本，不能无差别全作废或默认沿用。批准过期、来源冲突/删除或不可读也须复核；工具不能核实的来源由责任人确认。

上线失败先停止扩大影响，由获授权负责人执行既定回退或补偿，复核数据和业务状态，记录沟通、缺陷、复测及再次发布 Owner。代码回滚不代表外部操作或数据自动撤销。未完成恢复验证不记该批次成功；成功批次与失败批次独立保留。

## PRD 前置资料

从新业务问题推进完整生命周期时，L0–L2 需要留下可交接的资料。先复用已有工单、访谈记录、问题报告、研究或决定，可合并到一份文档的清晰章节，不按阶段机械增加文件。原始输入和阶段分析各自保留来源；已有材料不足以支撑结论时，明确未知与待决，不直接把解决方案写成已确认需求。

| 阶段产物 | 应能回答的问题 | 交给下一阶段 |
|---|---|---|
| L0 问题受理单 | 谁在什么场景反馈了什么、来源与原话是什么、影响有哪些证据、目标与授权范围是什么、由谁接手 | 可定位的问题、相关人、影响与待查问题；不预先认定技术根因 |
| L1 现状调查与问题分析 | 当前业务如何运转、断点在哪、哪些是事实/反馈/假设、候选原因如何验证、已有能力/知识/权限/配置/数据缺口是什么 | 证据及其局限、原因判断、场景/规则与未知项；没有数据不编影响规模或收益 |
| L2 方案比较与分流决定 | 指导、权限/配置、数据/流程、研发或不做分别何时适用；为何选本期方案、排除哪些范围、谁决定、依据是什么 | 决定来源及状态、目标与边界、进入 PRD 的内容和仍受阻的事项 |

PRD 引用这些依据并形成业务规格；不需要在 PRD 里重复维护一套调查和决策全文。追踪记录分别关联阶段产物及其版本。关键规则、事实或方案选择未决时，按职责澄清受影响部分；不依赖它的调查可继续。

模拟案例明确标模拟资料、模拟角色和验证范围。事后补录须注明补录时间与依据，不能倒填首次发生时间、调查、签字或批准。仅要求 PRD、已有需求中途进入或历史证据确实缺失时，按实际范围交付，不能把新建三份文件作为通用准入条件。

## 非研发与多分支

指导、权限、配置、数据处理可独立结项，保留决定、负责人、授权和处理前后证据，不强制生成研发需求或声称已上线。调查后需改代码时建立关联需求，继续复用问题身份。配置知识至少说明用途、匹配/优先级（按实际系统取证）、适用版本/环境、权限、修改前快照、测试、复核、回退或补偿与支持人。

一个问题可关联多个需求，一个需求可有多个工作项和发布，一个发布可含多个需求。各分支保存自身状态和必需产物；可选或不适用项记录理由，不能删除未完成分支来宣称全部完成。共用制品用版本引用关联，而非复制维护。

财务类异常需先核验真实账务及防重复措施，再由有权人员决定是否处理；业务口述“线下已做账”仍是反馈，未核实凭证不自动重试入账。本规则不要求普通需求采集财务字段。

## 交接与恢复

业务无 AI：用组织现有渠道保留原话，产品/协调人整理后带回业务可读稿确认。业务有 AI：允许其整理草稿，但规则、权限与验收仍由相应负责人确认。草稿被修改后绑定新确认版本；不共享权限时提供获授权的摘要或人工交接，不绕过访问限制。

接手先匹配项目/需求 ID、唯一 PRD、记录 revision 与当前权威产物版本，再检查未决、失败和待复核项；未知历史保持未知。重复运行复用当前有效结果，不重复创建 PRD、工单或部署。外部动作幂等性由平台/适配器验证；本地 JSON 无法证明。

交接包按实际需要保留：目标/范围、问题来源、输入及版本、已有身份、已确认（谁/何时/什么版本）与待决、FR/AC、当前产物与真实结果、权限范围、接收责任人、下一动作/依赖/预期结果和已知期限。只阻断依赖未决或故障的部分，独立工作继续。
