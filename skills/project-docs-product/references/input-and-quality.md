# 资料条件与产品质量

所有PRD共用本约定。无源码不降低业务规格标准，也不阻塞完整需求、目标交互及流程的编写；它限制的是对现有实现及兼容性的证明。代码事实不是业务批准，文档写得完整也不等于已经定稿。

## 按现有资料开始

| 资料条件 | 工作方式 | 证据边界 |
|---|---|---|
| 有源码 | 定位相关界面、对象和调用链，与业务资料交叉核对；区分现有实现和目标规则 | 只读相关范围，不以源码自动证明生产版本或正确业务；不为PRD实现业务代码 |
| 无源码，有截图/设计稿/操作演示 | 在可信原页面上标新增/修改/删除，复用可见布局、控件和术语；询问不可见但影响结果的行为 | 画面只证明可见内容，不能推断后台校验、权限、存储及外部接口；演示不能擅自启动用户桌面应用 |
| 无源码，只有旧文档/纪要/口述 | 梳理角色、对象、输入、业务结果和异常，合并已决口径；关键缺口集中处理 | 来源注明口述或文档版本；无可靠旧页面时可画完整目标任务的线框/交互图，不冒充旧页面或宣称设计一致 |
| 新产品，无现有页面或系统 | 从真实用户任务设计目标页面和端到端流程，说明假设、范围及可观察结果 | 现状基线可不适用；不索要不存在的Git版本、类名、接口或历史回归 |

实际资料可混合使用，不要求先选固定模式。来源记录位置/版本、时间、覆盖范围和能证明什么；冲突按这些证据及明确修订关系判断，不按“源码一定比截图新”或资料类型自动排序。局部认可不能扩大全文确认。资料足够就直接写；不要把查不到代码当成必须重新访谈的理由。

业务规格无论输入类型都需交代任务入口、角色与权限要求、主要对象、字段含义与来源、触发条件、状态与结束结果、异常恢复、历史/在途适用性和验收。按复杂度合并，不凑章节；数据保存要求表达为业务约束，具体表/方法/接口名无依据就留给研发设计。

## 缺口如何处理

- 会改变业务结果、权限、范围或不可逆后果的缺口：按[生成前澄清与未决分类](workflow.md#生成前澄清与未决分类)先问关键问题，已有明确决定不重复询问；业务未决、技术待核实和待批准分别表达，草稿例外也按该约定处理。
- 不改变业务规则的可逆呈现选择：可以标明设计建议继续绘制，不把假设写成已确认事实。
- 接口/字段/存储/性能等实现细节：列研发需核实项，不以缺少类名阻塞业务规格，也不把会改变数值或业务结果的契约问题全推给研发。
- 冲突未解：保留各来源及受影响分支，不任选一个默认；先澄清，可整理不受冲突影响的部分。未回复不等于批准，不自动外发或进入研发实施。

## 检查推荐方案是否合理

推荐方案先用业务语言说明：谁的什么问题，通过哪项行为变化解决，完成后能观察到什么结果，以及仍有什么限制。重要取舍确有多个可行方案时给出推荐及理由，不为已决事项重开选型。目标没有量化依据时用可验证的业务结果，不虚构收益或指标。字段、页面和接口变更应能沿这条因果关系解释；只列改动点不足以证明方案解决了问题。

先确认每项变化属于用户要求或实现目标不可缺少的配套，再从用户任务走正常路径，用相关反例挑战方案。外围风险单独记录，不自动扩成当前需求；发现代码问题不等于获得改造授权。对未变外部流程，只定义本期数据交接，不逐分支重设其处理方式。之后检查：

1. 用户做错时能否退出、撤回或改正？不要为让流程走通，要求先完成已知错误业务。区分尚未执行、已发出结果未知和已经完成，不能统一套恢复或补偿。
2. 外部依赖失败或恢复后，当前对象有无合法可达的重试触发点？先核实已有能力是否足够，不把每个恢复问题都设计成新按钮。不要让尚未产生结果对象的用户依赖结果对象上的入口；每个相关状态写谁接手、在哪里处理及结束结果。
3. 可恢复缺失、永久缺失、不适用或历史豁免是否区分？“待完善”等承诺恢复的提示须与真实处理能力一致，持续缺失对目标的代价要进入取舍。
4. 部分成功、重复操作、跨角色接手、后续结算/衍生操作是否保持同一对象与计算口径？上游与结果粒度不同不能直接复制派生总额；人工和自动责任不能用一个含混角色替代。
5. 新增操作叠加既有筛选、默认值、权限或状态后，用户看到的提示是否准确？用户预览的输入/依据与最终结果不同时，是否需要重新确认，失败或取消是否保留原业务事实？隐藏条件不能只在PRD告知，需有合适的界面说明或恢复动作。

本期确实改变外部执行或事实记录时，正文和图都要区分确定失败与结果未知：业务拒绝、已证实未成功、仍无法核实不能共用“未知”出口；成功只连到有确证的结果。逐条检查判断节点的每个出口及恢复子图，包含核实后成功、确定失败、仍未知分别由谁继续或结束，不能用“否/未知”合并掩盖缺失分支。

记录保存失败不等于实际业务事实未发生。本期涉及实物交接或改变外部执行时，分别核对事实与记录；已发生但未记成功或待核实的对象不能当作从未发生而重复执行、释放资源或抹掉责任。写清原对象上的核实/补记方向，缺少入口、授权或保护措施时列相关设计阻塞，不强定技术方案。

只选与任务有关的反例，避免把某业务的金额、冲销或会计处理写成通用默认。发现不合理推荐先改方案和关联图/验收，再重走完整受影响旅程；不能不断追加补丁规则直到读者无法理解。

## 交付判断

| 用途 | 必须能回答 | 不能冒充已完成的内容 |
|---|---|---|
| 需求讨论 | 问题、目标、范围、候选方向、影响关键选择 | 关键规则未知时不称业务定稿 |
| 业务评审 | 用什么入口完成任务，正常/错误后怎样继续，哪些建议需决定 | 无依据断言、错误推荐或流程断点不能仅标“待确认”就放行 |
| 技术设计 | 业务行为、约束、边界及验收明确；具体阻塞与技术待核实分开 | 没有源码可支持目标方案设计，但不能称实现兼容性已核实；业务未决只阻塞相关部分 |

先验收范围和阅读结果：读者能否直接指出本次变化，每项新增能力是否有需求依据，是否混入技术制作说明或外围改造；不通过先删减或重组，不能靠补齐异常把错误范围闭环。测试再独立核对正常、边界、异常及相关历史场景的可观察预期；关键组合案例必须能从给定输入推导每个对象的结果，不以原则、编号或回指替代具体预期。正文优先业务语言与实际图示，技术定位/组件/Git/工具取证放独立证据文件并链接。简单需求用一句交付结论，复杂需求按用途列可推进部分和具体阻塞，不强制新文件或审批流程。

有无源码都须实际读取成品和图，分别判断业务读懂、研发设计约束、测试预期及证据边界；结构检查、图片数量和模型自述不能替代。复杂任务用独立上下文内容复核；修局部后还需走完整旅程。模型角色试读不是实际岗位试读，通过有限样本不能承诺每篇优秀。
