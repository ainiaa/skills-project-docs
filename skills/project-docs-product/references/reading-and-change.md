# 阅读视图与现有功能变更

## 面向读者的最低交付要求

默认顺序为变化概览→页面与交互→业务流程→字段及规则→异常/历史→中文验收场景→未决/研发补充。按问题合并，不强制所有需求同样篇幅。正式 PRD 是规则真源，MD与HTML使用同一业务主文；FR/AC 是追踪编号，不是业务术语。文件组织按下节选择，来源与确认按[工作流](workflow.md)，资料和业务质量按[资料条件与产品质量](input-and-quality.md)。

## 轻量需求与拆分选择

只有单条文案、校验或阈值变化，且没有新增页面结构、角色交接或复杂状态时，用短变更说明、明确规则及必要正常/边界/异常验收即可；合并或删除模板中的无关章节，不生成空表、无意义的“不适用”段落、角色摘要或流程图。文案变化不自动触发页面图；确有布局或交互变化仍按下节给图。篇幅与文件数量不作为质量门槛。

简单需求默认在同一短文末保留校验需要的最小 FR/AC/SRC 追踪；主文先讲变化，追踪引用主文，不复制规则。用户要求精简阅读或明确拆分、以及详细验收/来源已妨碍阅读时，使用业务主文与同目录的独立追踪文件。主文有产品版本、状态、规则和可观察预期；追踪有相同版本、稳定编号、来源、确认记录及主文锚点。附件不得独自增加规则或修改确认范围。正文规则必须独立读懂，不能让读者来回拼接才知道结果。

拆分用 `--file prd.md --tracking prd-traceability.md` 联合校验；主文须链接实际追踪文件。单文件不保留指向不存在附件的模板链接。详细验收按需外置，仍引用主文规则。已有单文件及旧折叠追踪附录继续兼容；增量迁出须保留编号、确认记录及可点击去向，不要求无关旧文档批量改格式。编号和历史确认的保留规则见[确认与修订](workflow.md#确认与修订)。

既有页面先遵循[brownfield增量设计约定](brownfield-delivery.md)复用真实布局及组件，不从头另造替代页面。有页面变化就提供实际目标页面线框或交互示意，直接嵌入正文并配操作说明；缺可信旧页面时标“目标草图”，不编造前后截图。跨系统或多分支流程按问题选图：涉及职责交接提供业务泳道图，局部判断需要时提供流程图，清楚呈现顺序、责任、异常及结束结果，不能用箭头文字或覆盖表冒充图。只交付PRD不等于不画交互图；交互示意也不等于完整可点击产品原型，不以此扩大研发范围。纯后台单条规则无页面、无复杂分支时可省图并说明适用性。

每张图须实际渲染并实际查看，检查可读性和规则一致性；最终交付打开主文检查图片真实存在且直接可见。未决布局/精度/失败策略在图及说明中标明建议或待决定，不能用画图偷偷确定。验收同时核对读者能否回答“改哪里、怎么操作、数据怎么算、出错怎么办、还要决定什么”；测试数量、编号齐全和旧规则未丢不能代替此项。

## 正文与交付回复

资料充分时直接整理，不重复确认已明确决定；冲突处理按[资料与质量](input-and-quality.md#缺口如何处理)。需要澄清时只呈现简短决策摘要：本期范围、已知结论、假设及待决定问题，不先询问文件名或无关细节。

正文只写产品规格：用户、变化、规则、状态、边界与可观察结果。增量需求开头直接列位置、具体变化及业务影响；未变功能不逐项介绍。一条规则集中定义，页面说明、图和验收引用它，不再各讲一遍。详细验收可具体化输入和结果，不能独自引入主文没有的适用对象、计算基数或余额变化；发现时将必要约束用一句话补回主文，或移除超范围预期。页面图内不放框架、控件库、渲染尺寸或制作限制；设计标注仅解释新增/修改位置，不能冒充产品提示。Skill、memory、工具诊断、运行命令及详细检查限制放独立证据文件；来源、确认记录和版本继续可追溯，FR/AC 保留必要来源引用。不要在每条规则重复生成过程或验证免责声明。简单需求用短摘要和必要验收即可，既有单文件仍兼容，不为模板扩写。

交付回复先回答改了什么、需要决定什么、下一步，并链接正式成品；没有待决定事项时直接说明。简述实际验证范围和影响使用的未覆盖项即可，完整命令、日志和重复的检查边界放已有证据链接，不在回复重新铺开。简单整理或小修订用几句话交付，不强制覆盖表；用户要求详细证明时再展开。风险、阻塞和未获确认的规则不能因精简而隐藏。

定稿或大改后的交付回复按需要附一屏用户要点→FR/AC/页面或章节→结论→已落实/范围外/未覆盖的覆盖表，不复制规则。覆盖核对按workflow.md执行；对话不可完整恢复时说明边界，不宣称全部历史沟通已覆盖。

## 同一份正式 PRD，按任务阅读

先讲变化、已明确规则与真正待决，再链接详细材料。证据附录保存评论ID、旧口径和取证过程。原编号不补零、不重排（如 FR-01、AC-01、Q1），新编号沿既有风格；误改号按可信原稿恢复并保留映射。确认继承及需求保留统一按[工作流](workflow.md#确认与修订)，阅读精简不能删除业务约束。

来源链接必须保持可点击，优先使用相对路径。已有仓库 PRD 需要引用交付目录外的源码或冻结资料时，校验命令显式追加 `--source-root <已知来源根目录>`（可重复）；只允许这些根内的实际文件，不自动扩大目录、不放宽原型资源边界。无法校验时报告缺口，不能改成行内代码、删链接或复制无关源码来凑通过。

摘要直接说明问题、前后变化、价值、边界和关键待决，并链接正文；不复制另一套规则。需要时用已有章节回答业务、研发、测试的阅读问题，简单需求合并为几句话，不强制角色摘要或新文件。没有调研数据就不造收益、负责人或排期。

原型范围内先列页面清单，记录页面名称及原有标识（无标识时用简短稳定名称）、本次新增/修改/衔接、角色、入口、去向、关键状态、数据条件及 FR/AC。业务页面与 HTML 文件数量无关；一个文件可承载多个页面，也可使用相邻文件。沿用实际导航和信息架构；弹窗、抽屉和页面内状态按真实交互选取。任务必须经过但未修改的页面保留必要衔接，范围外入口与结果明确模拟边界，不要求复刻整个旧系统。

交付范围按授权，详见workflow.md：PRD示意不自动升级成完整原型，已授权的完整原型也不因分阶段或局部修订缩减。

| 读者 | 首先阅读 | 必须能作出的判断 |
|---|---|---|
| 业务人员 | 业务摘要、典型场景、前后变化、核心流程/原型、关键规则与例外 | 是否解决问题，是否改变职责，哪些规则需要确认 |
| 研发人员 | 相关现状及依据、FR/AC、变更与影响、状态/权限、依赖和兼容 | 能否形成技术设计，还有哪些阻塞决策 |
| 测试人员 | FR/AC、边界与异常恢复、状态/权限、历史影响及回归范围 | 如何验收，哪些旧行为要保持，如何准备数据 |
| 产品与设计 | 用户任务、规则、页面信息、角色交接、交互反馈 | 用户能否完成任务，各种状态是否清楚 |
| 运营或负责人（按需） | 操作变化、切换范围、效果观察、异常处置 | 如何落地并判断效果 |

阅读视图不隐去影响该读者决策的规则。另行摘要标明正式主文及版本，规则变更后重生成受影响内容；演示正确不等于业务确认。无pdlc-prd仍按相同业务要求交付。

## 现有功能：现状依据、变更前后与历史影响

仅记录理解本次修改所需的历史背景。先沿 Overview 的取证方法读取相关需求、测试与源码；已有新鲜图谱时先定位影响链。现状依据记录资料位置、版本/日期、能证明什么和缺口；源码事实与目标业务决策分开，不能用旧代码否定新规则。无源码仍可写业务现状和影响，技术影响标待核实，不虚构文件、调用链或接口。

复杂影响需要对照时使用下表；普通增量用开头变更清单即可，不再按 FR 重复一份：

| 关联 FR | 当前行为及依据 | 目标行为与理由 | 影响对象和影响判断 | 历史/进行中处理与兼容 | 回归 AC 或待核实项 |
|---|---|---|---|---|---|

影响只展开相关项：用户职责、页面、权限、状态、历史数据与进行中业务、接口/消息与调用方、定时任务、报表和外部系统。每项说明依据或假设、影响结论、需要保留的行为与验证方式。未检查写“待核实”，检查未命中写“未发现影响”并注明范围，有明确证据才写“已核实无影响”；不能把无资料变成无影响。没有技术仓库不阻塞业务草稿，但不得声称技术影响已覆盖。

特别核对新规则适用的新建对象、历史记录、在途/进行中任务和跨版本消费者。保留旧规则还是迁移由业务决策及技术设计承接；未知时进入关联 FR 的未决事项，写明是否阻塞研发交接，不擅自承诺迁移、回滚或上线日期。涉及切换时按需说明生效边界、回退后的业务结果、监控和效果观察；PRD 定义业务约束，研发核实实现方案。

局部修订保留编号及无关人工内容，列出受影响的 FR/AC、图、页面、旅程与摘要；改变规则后补回归场景，核对历史确认是否仍有效。简单规则调整可用一行前后对照和少量 AC 表达，不强制生成矩阵或图。新功能没有相关历史行为时说明不适用即可。

## 研发速览（按需）

需要研发交接且有相关资料时，在已有研发阅读区补一份简短速览：本次变化、必须保持的行为、已核实的系统/模块和接口依赖、候选改动点及依据、业务阻塞与技术待定项。复用正文 FR/AC 和影响表，不强制所有需求填写文件或新增章节。没有代码时按已知模块描述，具体文件待核实。

代码证据优先定位字段、枚举或方法的定义处，不用调用示例推定真实约束。候选改动点只是定位线索，不等于技术方案已经批准；新增接口、事务、存储和组件拆分由技术设计决定，不把猜测的文件名或接口路径写成事实。速览中的每条结论在正式正文或来源中有依据，不能只在摘要增加要求。

## 计算与修改联动核对

实际计算、分摊、累计或前后值变化仅靠文字难读时，在对应规则旁给一张小型数据示例表，列输入/单位、采用依据或公式、输出及必要前后值；简单关系用一句示例即可，纯文案或无数据变化需求不强制加表。用同一组模拟数据串联关键步骤，区分源总额与本次金额，标明方向、精度/舍入及候选假设；未定参数不能画成已确认结果，也不虚构真实样本。核对正常值、阈值两侧、精确边界及非法输入，派生结果须由给定基准复算。非计算需求不增加固定计算章节。

每次规则修改后，沿受影响 FR/AC 核对正文、摘要、图、页面、旅程、接口依赖和未决项是否同步；只更新受影响内容。不同业务含义的相同数字不能机械替换，字符串出现次数不能证明一致。保持稳定编号，允许删除后的空号，不为连续性重编号。示例表用于解释规则，详细用例放验收文件，不把样例条数当完整性。用实际内容评审和适用的计算断言验证语义，结构校验只证明标识及资源关联。

## 图与页面按问题选择

| 需要说清的问题 | 选择 | 取舍 |
|---|---|---|
| 单角色步骤和分支 | 流程图或简洁流程表 | 简单规则用 AC 即可，不强制画图 |
| 多角色/系统的职责、交接、等待与异常 | 泳道图 | 明确交接接收入口和结束责任 |
| 对象生命周期及合法转换 | 状态图 | 状态复杂时补充，不与泳道重复堆图 |
| 跨系统同步/异步、回调、顺序、超时/重试 | 时序图 | PRD 表达业务时序；服务、事务、队列方案待研发核实 |
| 页面信息层级与布局 | 线框或原型截图 | 已有交互 HTML 时可直接截取，避免两套独立稿 |
| 从入口完成任务与失败恢复 | 交互 HTML | 复用 prototype.md 的共享对象、角色、状态与旅程验证 |

根据用户要求及风险选图；用户明确要求的图不能省略，未要求时不固定全套。优先复用 Diagram 的非源码原生通道及已安装官方渲染器，不新增出图工具链。每张图在 PRD 中链接可编辑图源和实际导出，注明产品版本、对应 FR/AC、业务依据及未决假设。无仓库事实时不伪造源码证据；涉及真实代码事实按 Diagram 的证据要求核实。

图文一致性按[需求保留与恢复走读](workflow.md#需求保留与恢复走读)执行，增量图按[brownfield图示验收](brownfield-delivery.md#图示与阅读验收)检查。修改 FR 后仅重渲染受影响图、重验相关旅程并更新摘要；业务时序不能冒充已存在的服务调用，模拟原型不能证明后端权限或支付成功。

需要机器核对时使用现有 bundle 的可选 diagrams 清单，详见 prototype.md；不要求普通 PRD 或简单需求额外生成索引。哈希和编号一致不能证明图中文字与业务规则一致，复杂任务需独立内容复核。

## 分角色交接评审

按[工作流走读](workflow.md#需求保留与恢复走读)核对内容，用上方读者表回答业务、研发和测试各自能决定什么。复用现有review.md或回复，列版本、实际审查者、具体问题和阻塞部分；不另造审批状态。`--review`只观察标题，handoffReview.status=not_run不是内容评审通过。独立复核及证据边界按[评测约定](evaluation.md)。

## 交付验收汇总

在交付回复或已有评审证据区，用简短表格列产品版本、文档修订及本次核对范围；结构检查、浏览器旅程、模型内容评审、人工确认分别记录结果、证据链接和剩余问题。复用已有命令输出、browser.json、bundle 和评审记录，不增加状态文件或审批框架。没有原型时浏览器写不适用，不把未执行写成通过。

文件、规则、工具或上游身份改变使旧证据失效时，标明具体变化及需重验的检查，不把其他版本的成功替代当前结果；未验证、失败、失效与不适用分别表达。哈希只能证明字节关联，不能代替业务含义、人员确认或真实效果。真人试读及生产验证没有执行时单列未验证。
