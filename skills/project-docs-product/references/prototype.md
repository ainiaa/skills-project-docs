# 交互 HTML 原型交付

本节针对明确授权的完整可点击原型。PRD 内嵌的页面交互示意和业务流程图按阅读约定提供，不因未请求完整原型而省略。

先明确原型回答的问题：布局、操作流程或业务状态。根据 PRD 生成原型时，默认覆盖本期范围内的完整用户任务。只有用户明确只验证某个局部时才采用“局部交互验证”，并写出未覆盖范围；不能自行把完整请求缩成一个表单或单条规则演示。只有需要比较布局时提供多方案。已有产品先按[brownfield约定](brownfield-delivery.md)读取当前页面和组件，再沿用其导航、组件和术语，按需使用 frontend-design 或 UI/UX 能力。原型样式不能自行新增业务规则。

## 先确定流程覆盖，再生成页面

在 PRD 中写流程覆盖表：每条关键旅程记录角色、业务入口、步骤和页面、前后状态、结束结果、异常恢复，以及对应 FR/AC。角色交接必须有接收入口；用户要能找到任务、完成操作、核对结果并继续后续工作。没有后端时用明确标识的模拟动作补足本期流程，不能以“尚无接口”省略结果与失败状态。范围外步骤明确标出边界，不虚构真实业务规则。

同时列本期页面清单与跳转关系，按真实产品区分列表、创建、详情、待办、结果及必要弹窗；不能用状态按钮替代实际业务页面和角色交接。一个 HTML 的多页面路由/视图或多个 HTML 都可，验收依据是页面覆盖、可发现入口和连续操作。原产品将创建做弹窗时保留弹窗，不为了凑页面强行拆分。标明未修改但流程必经的衔接页面、范围外系统和实际模拟边界。

多视图必须共享模拟数据和稳定业务对象 ID。列表、详情、待办、指标和操作记录围绕同一个对象联动；不能给每个页面各放一套互不关联的数据。状态变更统一经过角色、前置状态和输入检查；禁用按钮只是反馈，动作本身也应拒绝无效操作。确认、失败、返回和重试等路径按实际流程提供，终态不能重复执行。

## 现有页面的变更标注（增量需求按需）

先记录基线来源、版本/日期、核实范围和缺口，优先使用实际页面、截图、设计稿、历史 PRD 或源码。口述现状标明口述；没有可靠基线仍可画目标页面，但不能把模型重画的旧页面当真实现状或声称差异完整。不是每次都复制整套旧页面或追求像素级复刻。

同一原型提供使用模式与变更标注模式，共用业务页面、数据和交互，不维护两套原型。新增、修改、删除、保持不变用文字及边框/图标表达，不只靠颜色；待确认是可叠加的决策状态。新增说明出现条件；修改说明前后差异；删除在对照区域展示旧位置及替代入口，不能在使用模式保留可执行旧操作。保持不变只标与本次理解有关的规则，避免满页标签。待确认内容注明对应 Q，不把假设混成已决规则。

每处变化链接本次 FR/AC 和正式 PRD；前后对照放原需求的变更说明，详细规则只维护一次。标注内联展开，不遮挡主操作、不改变业务数据；切换后保持表单输入、当前对象、角色、状态与焦点。若标注与源需求冲突，先记录并处理，不能以视觉标签覆盖规则。

字段按实际影响写清含义/来源、控件/选项/默认值、必填条件、校验/错误、可见及可编辑角色、流转页面、历史缺字段与新记录空值、查询/导出/报表/接口/消息及正常/边界/异常回归。未知影响写待核实，不默认所有页面都增加，也不默认历史数据都补填；简单命名修改明确原规则保持即可。

截图从同一原型实际渲染，按用途提供使用模式与变更标注模式；有可信基线且需要比较时再提供修改前截图。标注截图也要记录角色、场景及模式；变更后更新受影响截图。标注完整性和业务含义由内容审查确认，不以标签数量代替。

需要机器核对时沿用 HTML 标识：业务页面/弹窗根元素可用唯一的 `data-page="request-detail"`；变更区域用 `data-change="added|modified|removed|unchanged"`（取其中一个值）及非空 `data-change-note`。变更区域声明有效的 data-requirement/data-scenario，可复用上层 FR，但 AC 须在该区域明确列出；它们归属于包含该区域的页面。待确认写在可见说明和对应 Q 中，不另造一套状态机。旧原型不强制补这些属性；属性只证明声明，不验证标签内容、页面是否实际可达或语义差异完整。多个本地 HTML 使用相同版本、全交付唯一页面标识和共享业务对象；静态关联不代替真实跨页操作验证。

## 旅程验收

先写可执行旅程测试，再实现交互。真实从业务入口走到结束结果，途中切换角色、返回列表、核对同一对象与记录；相关分支逐条验收。覆盖表中每个本期关键任务必须有实际浏览器结果；未覆盖的说明原因，不用截图或编号统计代替。局部交互验证只报告该局部。

## 交付格式

从 `../assets/prototype.html` 的标识约定起稿，根据实际需求重写全部业务内容。普通原型使用自包含 HTML/CSS/JS、系统字体、内联图标及内存模拟数据，不依赖 CDN、后端或包安装。复杂交付使用相邻本地资源，保留目录结构。明确标为“交互原型 · 模拟数据”；展示实际版本及尚未确认的规则。

可校验的静态资源包括 HTML 直接链接、响应式图片、Markdown 内联与引用式链接，以及内联/直接链接样式表中的 `url(...)`。CSS 不使用转义或 `@import`，改为直接链接的本地资源；此限制会明确报错。结构校验不执行 JavaScript，不能替代浏览器检查。

- `<meta name="product-version" content="与 PRD 相同的版本">` 绑定交付版本。
- 每个需求区域设置 `data-requirement="FR-001"`；多个编号用空格分隔。
- 场景入口设置 `data-scenario="AC-001"`，并关联对应需求区域。覆盖 PRD 中声明为原型范围的需求与场景；未覆盖的说明原因。
- 承诺超限报错并保留输入时，不用 maxlength 等先行截断输入；在提交动作校验，用真实键盘输入（按需含粘贴）验证超限、修正和边界，不能只通过脚本赋值绕过原生输入行为。
- 表单有 label、键盘焦点、明确的错误反馈；禁用状态不能执行对应操作，弹窗可以取消和返回。
- 操作后的用户可见状态和结果可核对；相关空数据、失败、权限差异按需提供场景，重置后可重复演示。角色切换仅为模拟，不能宣称验证了服务端权限。
- PRD 与原型冲突时标为待处理，探索变动先作为建议，经确认再同步需求。截图来自实际浏览器渲染，变更后重新生成受影响截图。

先编写关键交互的可执行测试，再实现原型业务逻辑；即使上游 throwaway prototype 允许省略测试，也服从用户的 TDD 要求。真实打开成品，点击正常、边界、异常和非法场景，检查窄屏、文字溢出、焦点与反馈；实际查看截图。示例 `node --test scripts/test_product_browser.mjs` 验证集合自己的样例，不证明任意新原型已被验证。

在同一交付目录提供 PRD、原型、必要截图及评审记录，以相对链接关联。能打开的文件不等于已通过交互、语义或视觉验收；分别报告实际结果。只在用户授权时分享或发布。

## 轻量证据索引（需要原型验收时按需生成）

复用已安装的 Mermaid/Puppeteer 运行时，不为产品工作流安装新的浏览器工具链。运行器复用 engine_paths 的显式 CLI → 受管入口 → PATH 顺序，识别 CLI 软链接及简单 `#!/bin/sh` / `exec node ... -p ...` 包装脚本（只解析，不执行脚本）。`PRODUCT_BROWSER_MODULES` 优先于自动模块发现；浏览器按 `PUPPETEER_EXECUTABLE_PATH` → 包装脚本配置的 executablePath → Puppeteer 缓存 → 已有系统 Chrome/Chromium 查找。显式路径无效不静默回退；复杂包装脚本使用显式模块和浏览器路径。仅继承浏览器路径，不继承包装配置的其他启动参数。启动前汇总缺项，给出修正指引，不安装或下载。先验证宿主可打开浏览器；不可用时如实记为未验证。每次交付生成自己的 `journey.test.mjs`，由测试断言实际业务行为；退款示例不能充当新需求的测试。

通用入口：`node <本集合>/scripts/product_browser.mjs --directory <交付目录> --test journey.test.mjs`。测试从该模块导入 `launchBrowser`、`openPage`、`capture`；通过 `openPage(browser, 'prototype.html', {width:390,height:844})` 打开本次成品，操作并断言后执行 `capture(page, 'mobile.png', {role:'审批人',scenario:'AC-001'})`。测试必须关闭 browser。入口将运行当次 Node 测试，拒绝零用例/跳过/页面错误/测试期间输入变更，在 `evidence/` 写日志、截图和 `browser.json`；旧输出不算本次结果。目录内只放本次交付物，`evidence/` 仅作输出；业务输入不能放进这个目录。

可选 `bundle.json` 只索引已有材料，不复制规则。格式为 `schemaVersion:1`、`version`、`artifacts`、`journeys`、`browser`：

- `artifacts.prd`、`prototype` 是 `{path,sha256}`；拆分交付显式增加同结构的 `artifacts.tracking`，与主文同目录、同版且主文有链接，不自动猜文件。`tests`、`screenshots` 是该结构的列表，路径相对交付目录、哈希来自实际文件。
- 可选 `artifacts.baselines` 按从旧到新排列；旧单文件条目仍为 `{path,sha256}`，拆分历史用 `[{path,sha256},{path,sha256}]` 显式成对声明主文和同版追踪，不把两个文件当成两版。当前追踪及全部历史文件都进入浏览器输入快照，任一变更须重新验收；确认继承仍按 workflow.md，不因索引齐全自动获批。
- `journeys` 每项包含 `id`、`requirements`、`scenarios`、`test`、`screenshots`，分别关联旅程 ID、FR 列表、AC 列表、当次测试入口和截图路径列表。多个旅程集中在一个测试入口中，覆盖所有声明进入原型的 AC。
- `browser` 指向当次 `evidence/browser.json`。用 `python3 <本集合>/scripts/product_bundle.py --file <交付目录>/bundle.json` 检查路径、版本、映射、哈希与浏览器记录。只写 PRD 时可省略整个 bundle；单文件索引仅需 `artifacts.prd`，拆分索引还须 `artifacts.tracking`，不要求浏览器或截图。

`review.md` 用可读语言分别记录结构结果、旅程行为结果、视觉/可访问性复核、业务待确认事项。输入或测试修改会让旧浏览器证据失效；截图的视口、角色、场景与文件必须对应。本地记录可由文件编辑者修改，不提供签名或防篡改证明，也不证明 AC 的业务语义或人工确认；模型评审与工具观察分别注明。

## 最小设计约束

复杂演示可按需提供折叠的场景引导，说明起点、操作角色和预期终点，复用真实页面入口及同一业务对象。导航不自动执行审批等业务动作；无适用数据时明确提示，不偷偷创建或重置。允许退出并保留业务状态，确认重置后可重复演示。简单原型不强制增加引导。

优先沿用已有产品设计系统，其次采用用户提供的参考，最后才使用少量 CSS tokens（颜色、文字层级、间距、圆角、反馈状态），保持导航和同类组件一致。不新增设计平台或组件仓库。演示设置/重置与业务主操作分开呈现，界面不暴露不帮助用户决策的实现细节。

窄屏（至少 390px）要直接发现任务、状态和主操作，不能靠横向滚动找“查看详情”。普通文字对比度至少 4.5:1；状态还要有文字说明。键盘可打开、提交、取消和关闭弹窗，错误定位到需修正的字段；动作改变状态后把焦点移到可感知结果，避免留在禁用按钮上。截图前等待字体、图片、有限动画和两帧布局稳定；记录视口、角色、场景。同环境比较视觉结果；截图存在不等于视觉评审通过。

## 按需关联业务图

按 [阅读与变更约定](reading-and-change.md) 选择图型。PRD 的图表索引链接图源及实际导出，并关联相同产品版本、FR/AC；规则正文仍是唯一真源。图源与导出放在交付输入目录，不能放入浏览器输出 evidence/。需要确定性检查时，bundle.json 可增加可选字段：

```json
"diagrams": [{"version":"draft-1","requirements":["FR-001"],"scenarios":["AC-001"],"source":{"path":"flow.puml","sha256":"实际图源哈希"},"exports":[{"path":"flow.svg","sha256":"实际导出哈希"}]}]
```

每项恰含以上五个字段；FR 非空，AC 可空（概览图），但不得引用未知或属于其他 FR 的 AC。图源、导出与原型使用本次真实文件；版本须等于 PRD，不重复声明同一图源或同项导出。只交付 PRD 与图时同样可检查；没有图可完全省略 diagrams，不改变既有 bundle。与原型一起验收时，图源及导出必须出现在浏览器当次输入快照中，变动后旧证据失效。

该索引仅证明声明的版本、资源字节和标识关联；不读取或解释图中文字，不证明导出由声明图源生成，也不证明业务完整或官方渲染通过。官方引擎回执、实际视觉检查、FR/图/HTML 语义一致性分别记录。PRD 有图但未声明索引时，只能报告本次已执行的关联检查，不能声称全部图已自动核验。
