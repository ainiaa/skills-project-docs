# 既有产品：增量设计与业务闭环

已有页面、对象或业务流程的需求先读本约定，再写PRD。目标是接续真实产品，不把一张好看的目标草图当作改造方案。

## 页面基线与增量

先按[资料条件与产品质量](input-and-quality.md)核对可获得证据，查实际页面、组件规范、设计稿、截图或业务口述，记录来源、版本和适用范围；现状冲突按时间、覆盖范围及明确修订关系处理，不按资料类型自动定优先级。优先复用现有页面结构、筛选分组、工具栏、表格、详情/弹窗、日期控件和错误反馈。标清新增、修改与删除项；未变功能只在影响理解或兼容时简述，不借新增字段重做导航、配色或布局。截图未连接生产只能称源码复现或设计稿，不称现网截图。

页面线框不能用流程节点代替：把字段名称装进Mermaid框并写“保持”，只能说明信息关系，不能证明页面沿用。有可见基线时，直接在基线上标增量，或用静态HTML/SVG复现相关页面后截图；保留旧区域的上下/左右关系、对齐、表格、输入和按钮形态及可见配色，新增内容局部标注。静态页面图源仅用于PRD插图，不等于完整可点击产品原型。内部对照基线与目标图核对这些具体保留项；正文默认只放目标图和变更标注，不铺陈完整旧页面，只有差异难以理解时才并排展示；若确有重排，说明理由并标为待评审变更，不得自称未改布局。

无法获得可靠旧页面基线时仍可画完整目标任务，未知旧页面区域写明边界，并列需核实项；不得将从头画的替代页面包装为符合现有设计。不能因已有代码未知就跳过可查的同目录设计稿、前端仓库或组件规范；也不启动用户未授权的可见应用求证。自绘图的清晰和美观不证明基线一致。

## 字段生命周期与源/结果对象

新增或改变字段时，沿实际使用链核对保存、计算、会计/外部传递、列表、明细、筛选、导出、历史空值及验收。逐项判断受影响、保持或未核实并给依据；检查清单不等于每项都要新增功能。现有抽屉/页面及入口条件也属影响面，不能假定存在独立详情页，或因金额/状态变更让历史记录失去查看入口。页面、返回模型、导出各有组装链时分别核实。

不要从需求标题所指的列表或结果记录开始猜流程。先用用户要求的对象、变化和结束结果界定范围，再向上追溯必要入口和源对象，向下核对结果保存及本期使用方。取证可以发现外围风险，但没有范围授权就不能把它们写成新能力、待决定项或本次设计阻塞；外部系统只说明本次交接所需的输入输出，内部处理沿原规则。对新增字段按影响写简表：业务含义/粒度、来源、准备时点、固定时点、保存位置、使用方、失败/历史处理。区分业务约束与候选技术实现，不要求PRD写SQL或指定事务方案。

比较“上游准备、执行时引用”和“执行时取数”的收益、失败影响和适用条件；不能把用户的探索建议当成已批准架构。源对象总额与单次部分操作金额分别计算，不把源对象的派生总额直接复制给结果对象。区分可更新的准备值、用户看到的预览及成功业务结果：固定时点须有业务理由，不能默认“首次取得即永久固定”；取消或保存失败是否固定也须明确。预览到提交期间依据或结果变化时，说明是否刷新、重新确认及哪些内容不得静默替换。

多条规则可能同时命中时，写清适用顺序：已有有效保存依据、需要重新取数、来源不可用分别影响谁；外部故障不能无意覆盖原本可用的保存结果，也不要求失效依据继续使用。用一次“已有结果＋来源故障”的组合走读验证，具体优先级仍由本次业务决定，不把某个缓存或取价策略设为通用默认。

## 组合场景与决策

先按会改变结果的条件列场景，再核操作顺序：如原操作→结转→撤销与原操作→撤销→结转，即使同月/跨月标记相同，也可能有不同余额或字段结果。用既有正常规则推演，不为凑组合穷举无关状态；差异按下文分类处理，不能把后续一定再操作作为本次正确结束的前提。

只组合会改变本次新增数据或用户结果的场景，如源数据暂缺后重试、部分操作与派生记录、新旧切换。先判是否属于本期，再检查恢复；首次推送、冲销、主数据变化等仅在本次字段受影响时检查，不以此设计外围系统的补偿、发送控制或结算流程。状态可以是业务条件，不擅自新增数据库枚举或补齐按钮；先比较既有恢复入口，确需新操作时交代必要性与代价。恢复涉及源对象、多条结果或派生记录时，明确所选对象与实际更新集合、完整/历史对象排除、用户可见的关联影响，以及失败后哪些值保持原状；不能只写“保持一致”。每条异常写用户看到什么、责任角色、处理入口、允许动作、恢复终点与重复操作约束，并按资料/质量约定反查推荐策略本身是否合理；已有能力先核实，不用“沿用现有”掩盖未知。 关联操作须区分“参与核对的对象”和“允许写入的对象”：已有完整结果可能只作依据；缺失一方、历史豁免、单个冲突与公共依据不可用分别核对。按风险选择一个混合状态案例，明确保留值、更新值及失败影响范围，不穷举无关状态或新增未授权操作。

决策给一个推荐方案、可选替代与取舍，并在已有未决表说明决定角色、阻塞哪部分及哪些可先推进；业务结果待决定与接口/字段待核实分开。多项强关联选择写成完整候选旅程，不能分散为互不兼容的默认值。区分必要业务不变量与执行偏好：不遗漏关联结果不自动意味着全范围一次成功；按必须相抵/配对的最小单元比较一致成功与部分成功的代价，所选策略仍须有业务依据。没有业务授权则作为推荐草案，已明确规则不退回待定。角色、优先级或排期无依据时如实说明，不伪造批准。

涉及金额时用少量贯穿案例核对本期相关原操作、部分操作及派生记录，写出输入、顺序、每个受影响对象的预期值及不变值；涉及精度/尾差时可复算。精简可以合并重复规则，不能把这些预期缩成“验证一致”或仅保留编号。历史不回填不等于允许正常新缺数对象绕过校验。财务或可变主数据场景区分录入纠错与正式生效变更，业务采用时点及同币种/精度等改变数值的选择不能全推给研发。结果可在创建后补齐时，说明操作者/任务、时间、对象、采用依据及前后值的可追溯要求，优先复用既有操作记录，不自动增加审批或审计平台。

## 图示与阅读验收

一图回答一个问题：多职责交接使用泳道图，动作属于明确泳道，跨道箭头交代谁交给谁及交接结果；不能用带角色名称的普通流程图冒充泳道。局部数据分支确有必要时再补流程图，避免把同一规则重复画多遍。主图保持统一阅读方向；动作放责任主体，分支有业务结果，恢复箭头有明确去向。每个失败判断核对其影响是单条、关联单元还是全部；一条冲突不能在图里变成无依据的整批停止，公共失败也不能画成其他对象仍可盲目继续。区分本期数据子任务结束与原业务终止，不借新增字段异常无依据地改变原资格。未知路径用简短编号指向决策，不把长段待决说明塞进菱形。不将“核对模板”“检查一致性”等评审动作画成正常业务执行步骤。不混用业务阶段和未经批准的服务调用时序。

按PRD实际显示尺寸检查图中文字、分支标签、连线交叉和留白。不要用巨型纵向菱形链迫使读者反复滚动；过长则拆图或改变布局。实际查看导出并从业务入口走读到结束，不能只看引擎退出码或图片数量。

最后分别判断：业务能否描述正常和异常后的下一步；研发能否据此确定设计约束及阻塞项；测试能否准备有确定预期的数据。记录具体遗漏并修正文、图、验收及决策，结构通过不授予语义合格。复杂任务做独立内容复核，真人试读、生产联调、真实模型泛化评测未做分别保留缺口。
