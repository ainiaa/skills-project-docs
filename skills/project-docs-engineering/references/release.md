# 发布准备与结果闭环

作者：Jeff.Liu。PDLC方法改编来源与许可见[声明](../../../references/third-party-notices.md)。

## 变更日志与版本

未发布变更从Git差异/提交、正式需求和已知修复整理到项目已有CHANGELOG，分新增/修复/变更/安全等项目既有分类；不把未实现设计写成已交付。正式版本沿用现有版本策略和构建版本来源，检查待发布范围、未决问题、兼容性与迁移，并核对被测源码/构建。

ship的默认交付是具体可审阅的版本变更、发布说明和发布检查清单；是否提交、打tag、推送、触发CI或真实发布取决于用户已明确授权。已有授权足够时无需重复请示，但文档完成不授予这些权限。先查现有tag及其指向，按项目合并策略在正确提交上打标；结果未知先核实，不盲目重跑发布。

## 部署手册

沿已评审需求/版本和实际基础设施写手册：目标环境/范围、负责人、构建产物/摘要、依赖与配置来源、迁移顺序、发布步骤、冒烟/监控、回滚条件、恢复步骤和已知限制。命令来自项目实际流程，不套用示例Kubernetes、GitHub Actions或数据库凭据；密钥仅引用管理来源。

手册可供评审；实际执行必须具备授权、访问和环境。记录每环境/区域/实例范围的结果，被测构建与部署构建应可核对；部分成功、失败和未知分别呈现。回滚先评估数据兼容与恢复条件，文件存在不证明回滚能成功，冒烟成功不等于业务验收。

发布结果、复盘与业务效果交[Lifecycle协调资料](../../project-docs-lifecycle/references/coordination.md)，沿实际权威系统保留证据，不由手册宣布已上线。
